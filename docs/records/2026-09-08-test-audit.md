### 4. P1：补调度交接与竞争领取

`internal/service/run_scheduler.go:82–108` 专门处理“最后一次空领取后、新 Run 入队、旧 worker 尚未退出”的交接窗口；`:30–70` 包含 watchdog 恢复。当前 `run_scheduler_test.go` 主要测试 token/heartbeat，`internal/store/store_test.go:903` 的 FIFO 领取是顺序调用。普通 API 成功流程不能稳定命中这些交错。

### 10. P2：避免输出目录改变 Go 测试范围，固定覆盖率口径

本轮 `go test ./...` 实际发现了三个 `output/deploy/...` 临时 Go 包。`.gitignore` 只影响 Git，不能阻止 Go 递归发现。将临时工具放模块外或 Go 会忽略的目录，保留原证据；验收 `go list ./...` 不再因历史部署输出而改变产品测试包集合。

日常保留普通 Go 测试，定期或审核时用明确的产品范围生成跨包累计覆盖：

```sh
go test ./cmd/... ./internal/... -count=1 \
  -coverpkg=./cmd/...,./internal/... -coverprofile=<证据目录>/go-cross-package.out
```

按业务风险和分支选择补测目标，避免对“已由 API 测试覆盖的 Service 方法”重复补同义 CRUD 用例，也不要把低覆盖率全部归因于缺测。

## 建议实施顺序

1. **先恢复可信门禁：** 定位完整覆盖运行的两项超时，修浏览器陈旧断言、拆分关闭保护流程、纠正 Role 成功夹具，补一条 Action 真实保存/回读/冲突链路。导航操作路径的同期修复已经通过普通定点验证，不重复修旧路径。
2. **再补高风险状态边界：** 前端保存并发、Scenario 验收编辑、调度竞争、回执 SQL 状态机、部署失败回退。按模块分别验证和交付。
3. **最后完善结构与证据：** 实际重启、统一门禁矩阵、参考 harness 兼容、覆盖率口径、首次失败留证和完整源码摘要。

值得保留的覆盖包括发布依赖闭包与 CAS、Environment reset 摘要和当前主机范围、历史版本/组件删除并发引用及审计回滚、Scenario 取消和恢复信任、归档租约和引用保护，以及前端 SSE/未声明请求/React 异步警告检查。本轮不建议将这些重新组织成一个大而全的集成测试文件。
