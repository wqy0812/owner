# 架构师探讨纪要（不作为约束）

> 记录日期：2026-08-25
> 性质：本文件仅记录架构讨论中的问题、选择与思考，不是需求、设计合同、开发规范或实施约束。后续设计仍应以正式需求、当前代码和正式架构文档为准。

## 本次讨论的出发点

用户明确指出，本次讨论不是寻找代码 Bug，而是从软件架构角度判断：

- 平台的模块划分是否合理；
- 是否做到高内聚、低耦合；
- 是否存在过度设计；
- 是否真正理解使用场景并针对性设计；
- 是否能用尽可能简单、稳定的逻辑承载复杂交付需求。

## 问题与回答

### 1. 平台定位

**问题：** 这个平台未来主要服务哪一种使用场景？

**回答：** 内部交付平台。少量内部团队管理若干环境，重视标准化、审批、离线交付和可追溯。

### 2. 组件与场景的发布关系

**问题：** 组件与场景的发布应该采用哪种真实协作方式？

**回答：** 场景联合发布。场景可以引用已经验证的组件 Draft，并在场景发布时原子发布整套候选组件。

### 3. 制品能力边界

**问题：** 镜像构建、介质上传和跨仓平移应由平台负责到什么程度？

**回答（2026-08-27 重新确认）：**

- 介质或镜像既可以由用户通过平台接口上传/构建，也可以引用已有 IP 或地址上的介质或镜像，只要平台能够确认该来源可读取。
- 平台不实际拉取并保存介质内容，只保存文件名、校验码和用于定位内容的来源地址。
- Run 优先使用环境变量所指向地址中的内容；目标地址读取不到对应内容时，再检查录入的来源地址。来源可读时增加一个支线，由 Environment Owner 决定是否平移；来源不可读时，本次 Run 报错，并请组件录入者更新介质地址。
- 介质来源地址更新不影响组件 Release 状态。

### 4. 组件粒度

**问题：** 什么情况下才应该在平台中建成一个“组件”？

**回答：** 组件应是独立生命周期单元。只有能够独立版本、测试、复用或回滚的能力才建成组件，其余技术步骤留在 Playbook 内。

### 5. 角色分工

**问题：** Component、Scenario、Environment Owner 在实际组织中是否由不同责任人承担？

**回答：** 职责真实分离。三类 Owner 有稳定分工，联合发布和环境审批需要保留清晰交接。

### 6. 工作流复杂度

**问题：** 交付场景是否需要条件分支、循环、动态并行或自动重试等通用工作流能力？

**回答：** 保持静态 DAG。节点、依赖和目标组在发布前固定，复杂判断留在组件 Playbook 内。

### 7. 组件分类用途

**问题：** 组件的 layer、category、kind、requiredness 等分类主要要解决什么问题？

**回答：** 只需要少量标签。当前没有强分类治理或依靠分类自动编排的要求，保留少量标签用于检索和展示即可。

### 8. 组件间参数传递

**问题：** 组件之间真正需要怎样传递参数？

**回答：** 保留静态参数映射。下游组件需要引用上游公开合同值，但不要求运行时输出、表达式或动态数据流。

### 9. 候选组件的证据门槛

**问题：** 组件 Draft 进入场景候选集前需要什么证据？

**回答：** 安装与回滚均需验证。联合发布前既要证明组件能够安装和验证，也要证明能够安全回退。

## 本轮形成的讨论方向

以下内容是基于上述回答形成的讨论结论，不作为实施约束：

- 平台适合继续采用模块化单体，而不是为了形式拆成微服务。
- 独立生命周期组件、跨 Owner 候选交接、场景联合发布、静态 DAG、安装与回滚证据属于使用场景带来的必要复杂度。
- 条件工作流、运行时参数数据流、严格多维分类以及核心直接绑定具体制品工具，可能构成不必要复杂度。
- 组件目录、场景编排、环境管理、执行运行和联合发布协调应形成清晰业务边界。
- Ansible、FSS、Docker/Registry 等外部能力适合通过明确接口和适配器接入；“插件”在当前阶段不意味着建设动态插件市场。
- 简化的重点应是减少重复状态、跨模块直接修改和工具细节泄漏，而不是削弱交付安全所需的不变量。
