# 场景分支、版本演进、升级作业与业务验收

> 文档基线：2026-09-07 当前工作区。本文描述代码合同；本地测试结果与真实环境部署、升级验收分别记录。

本轮本地代码、转换工具和浏览器检查见[2026-09-05 验证记录](records/2026-09-05-scenario-lifecycle-validation.md)。

界面交付仅面向桌面浏览器，不要求移动端兼容。分支创建、新建版本、组件更换、验收编辑与排序、参数绑定、计划预览、测试、发布和正式升级入口，按桌面常用窗口宽度验证；遵循[开发指南](development-guide.md#验证怎么选)的 1280×800、1440×900、1920×1080 CSS 像素范围，检查导航、表格、DAG、检查器及弹窗操作可达性。

## 创建场景与新建版本

| 操作 | 来源条件 | 结果 | 发布前的测试 |
| --- | --- | --- | --- |
| 空白新建场景 | 场景 Owner | 独立场景的 r1 Draft | 干净环境安装测试及业务验收 |
| 从已发布版本新建分支场景 | 当前用户可见的已发布版本，允许其他 Owner | 独立场景、创建者为 Owner、r1 Draft | 干净环境安装测试及业务验收 |
| 同场景新建版本 | 本场景已发布版本，且有通过全部业务验收的成功正式安装或升级 Run | 同一场景的新 Draft，记录精确来源 Revision 和成功 Run | 安装测试、升级测试均通过 |

分支保存 `forkedFromScenarioId`、`forkedFromRevisionId` 和 `forkedFromDigest`，复制目标图、精确组件版本、参数、依赖、编排顺序和验收工作区。验收文件复制到新的目录，后续修改互不影响。分支不继承升级来源、升级顺序约束、测试证据、环境基线或恢复备份，也不能直接升级来源场景的已有集群。

场景分支创建时确认固定适配范围，首行展示标签；新增版本继承范围。新分支可选新范围，该选择进入预览摘要，修改后须重新预览；不能修改已有分支或历史 Revision 的范围。

同场景新建版本保留节点 ID，使用独立升级来源 `sourceRevisionId`、`sourceRunId`。来源测试成功、失败正式运行、已废弃版本、跨场景版本及没有业务验收的历史版本都不满足要求。历史已发布版本可以作为分支模板，在分支中补齐验收。

每个场景最多有一个活动 Draft。未发布版本允许在同一个 Revision 中继续编辑并使旧测试证据失效；待审批、排队或执行中的 Run 会阻止所有编辑。已发布版本和历史 Run 不可原地修改。图、升级顺序和验收编辑携带当前 Revision 摘要，过期页面须刷新后重试。

## 目标集群、升级作业和业务验收

目标集群始终保存完整目标配置。节点可选择同一组件的目标 Release，保留仍符合目标合同的参数；失效参数、依赖和版本路径需要处理后才能运行。

平台对比来源与目标的有效参数，生成独立升级图：新增执行目标 `install`；版本变化执行精确匹配来源、目标和发布线的 `upgrade`；同版本参数变化执行 `configure`；删除执行来源版本的 `uninstall`；无变化节点不重复安装。参数比较包含上游映射的变化。幂等 `install` 只有在同一组件、同一发布线、目标的直接父版本精确等于来源，且明确声明从目标恢复到来源的合同后，才可复用为升级动作。

来源组件检查与卸载使用目标环境实际基线 Run 的最终执行参数，包括当时已批准的介质位置；当前环境参数不会重新覆盖这些旧值。目标动作使用目标合同解析结果。

新增和升级遵守目标依赖；删除等待原依赖方迁移或删除，并遵守原依赖逆序。场景 Owner 可补充顺序约束，缺失能力、错误来源、依赖冲突或不能唯一确定的变更顺序均在预览中阻塞。卸载必须绑定独立的卸载后检查，不能复用安装状态检查。

升级执行顺序为：**全部来源组件状态检查 → 介质交付 → 变更动作及后置检查 → 全部目标组件状态检查 → 目标场景业务验收**。来源检查全部通过后才允许交付介质，交付前先持久记录环境已进入部分变更。安装也必须完成全部目标组件状态检查和业务验收。升级前不重复执行来源业务验收。

场景 Owner 维护至少一项有序 Ansible 业务验收作业，填写名称、验收目的、目标主机组、超时、风险、所需 CredentialRef 名称，以及是否可能产生临时变更。参数使用受控类型和公开来源绑定，不录入任意参数 JSON 或明文凭据。业务验收作为独立步骤记录，不伪造组件身份。

平台管理验收入口 `managed-scenarios/<scenarioId>/<revisionId>/tasks/acceptance/<jobId>.yml`，支持在线编辑、文件上传及 `tasks/`、`templates/`、`files/` 辅助文件。入口名称由作业 ID 生成。每次保存同时校验文件 SHA、工作区 SHA 和版本摘要。任务必须在成功路径清理临时资源；清理失败仍为验收失败。任何步骤失败立即停止并保留现场，不自动回退或重跑。

## 基线、证据和恢复

安装测试要求干净环境。升级测试要求环境实际处于来源完整版本，具有匹配的成功正式 Run、参数和组件安装记录；历史上曾经成功运行过不代表当前基线有效。新建版本的来源 Run 和目标环境自己的基线 Run 分别锁定。

`scenario_test` 和 `scenario_run` 使用 `executionMode` 区分 `install`、`upgrade`、`baseline_verify`。预览摘要、环境 Revision、基线代次、组件安装摘要、参数、工作区、审批和备份引用进入 Run 快照；预览、提交及执行前复核。提交使用用户范围内的幂等标识，重复标识不能提交不同内容。

安装和升级测试证据分别记录；首版只要求安装证据，派生版本同时要求两类证据。发布事务重新核对完整步骤、业务验收、当前摘要和候选组件状态。修改图、参数、顺序或作业内容后，旧 Run 仍保留，但不能继续满足发布条件。

环境安装状态区分完整版本、测试部署、部分变更和待复核，测试身份独立保留。首次可能变更环境的步骤开始前持久化变更标记；随后失败、取消或重启中断会保留部分变更状态和备份。只有全部目标验证与验收通过才更新完整版本。测试成功不能转为正式部署。

升级沿用环境串行调度和风险审批，删除组件必须经环境 Owner 审批。升级期间保留恢复备份。部分变更可预览受控续跑：后检查失败只重跑检查，主体失败须满足声明并验证的安全重试合同；不能续跑时先恢复现场。人工恢复后用 `baseline_verify` 复核已有完整历史基线。该模式不交付新的介质，不产生发布测试证据或可派生版本的正式运行证明，也不改变测试身份。旧版恢复不能显示为已清空集群。

基线复核成功后，以独立恢复证据解除旧未完成动作的阻塞，历史 Run 和动作回执保持不变。若失败升级包含旧版本之外的新增节点，必须先证明这些节点上的未完成操作已清理或卸载；仅验证旧版本原有节点不能恢复完整基线。

本次只支持直接来源到目标版本，不提供跨级或跨场景升级、主机迁移、扩缩容。安装记录无法区分的同组件多实例阻塞执行。

## 保留历史的离线数据库转换

当前数据库合同是 `clusterforge-v1-20260906-workbench-run-observations`。下列入口来自较早的场景生命周期改造；它不会为旧库推断分支标签。源库缺少固定分支范围或同分支存在冲突时，在创建目标前拒绝执行，须先盘点并单独确定数据处理方案。历史来源合同 `clusterforge-v1-20260905-role-jobs` 本身不足以通过当前前置检查。工具不使用业务清空或 foundation reset。

停用源库写入并确认没有活动 Run、审批队列或镜像构建后，指定不存在的新数据库和新工作区目录：

```bash
go run ./cmd/backup database convert-scenario-lifecycle \
  --db /absolute/source/platform.db \
  --target /absolute/output/platform.db \
  --source-playbook-root /absolute/source/playbooks \
  --target-playbook-root /absolute/output/playbooks
```

工具以只读方式访问源库，使用一致性 SQLite 快照复制完整数据库，再增加新字段与新表。校验覆盖源合同、完整性、外键、全部旧表的原有列和行摘要，以及工作区全部文件 SHA；还会将源文件与组件、场景持久化的入口和工作区清单核对，拒绝已经漂移的内容。转换后再次核对源库和源文件未变化。已有目标、活动工作、不支持的合同、符号链接或内容漂移会失败，清理本次创建的目标。

历史 Run 快照、步骤、日志、恢复引用和 Revision 内容保持不变。历史 `digestVersion=0` 继续使用原算法，不补造验收、升级来源或正式基线。历史环境新增待复核记录，不能仅凭历史成功 Run 宣称基线完整。显式基线复核会先寻找唯一匹配的历史成功 Run：完整节点、精确组件与 Release、安装 Run、备份身份和冻结参数必须与当前安装记录一致，且每个历史步骤成功；只发现候选不会写入完整状态。测试安装始终保留测试身份，信息缺失、混合来源或身份漂移会明确阻塞。数据库中已有的外部归档与备份路径保持原值，切换时仍需保证对应归档、备份介质可访问。

Catalog 备份另行包含已发布/已废弃场景的来源关系、验收合同及所有验收辅助文件，恢复前核对树摘要、入口 SHA 和来源摘要。Catalog 不包含环境运行证据，不能用 Catalog 恢复替代完整数据库转换或完整历史备份。

转换生成的数据库和工作区只有通过检查后才能安排环境切换。代码提交、部署和真实集群升级验收是独立交付步骤。
