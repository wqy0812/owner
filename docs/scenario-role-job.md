# 场景单作业执行

Owner 继续选择精确 Release、配置治理参数并连接组件依赖。检查不需要手工画成节点。依赖关系和手工顺序必须形成明确执行顺序。

部署按组件展开「前置检查 → 执行动作 → 后置检查」。回滚默认展开「回滚 → 回滚后检查」，可选回滚前检查及专用回滚后检查；默认后检查从实际来源动作解析并锁定。每阶段使用独立 Play；同一 Release 的不同节点分别执行。A 的任务、handler 和后检查都完成后，才开始 B。各 Release 的物理 Role 名由不可变 Release ID 派生。

每个 Run 只有一次正式 `ansible-playbook` 调用。平台和原生交付共用作业生成器、控制插件及 Python 恢复规则；平台使用显式的控制连接，独立作业使用本地持久化记录，连接失败不会切换记录方式。平台执行器、语法、连通性、介质和资源合同检查属于执行准备；组件 YAML 检查在依赖完成后按动作安排执行，实际结果记录到 Run。Run 保存作业摘要和真实进程退出码，阶段保存各自状态、主机结果和错误，不制造多个进程退出码。

callback 记录结构化事件；本地控制插件在阶段开始和结束时等待 Go 执行器确认。阶段结果、工作区校验和生命周期记录成功持久化后才确认放行。任务、handler、检查、不可达、超时、取消、事件序号缺失或持久化错误会停止整个进程组。已经派发的远端任务可能完成，停止不会撤销既有改动。

安装开始即记录恢复基线，主体成功与后检查通过分别记录。只有后检查通过才更新安装完成状态。回滚也只有在其后检查通过后更新恢复状态；部分安装和失败检查仍保留恢复记录。

安全续跑创建关联的新 Run：

- 前检查失败：重新执行完整流程。
- 主体失败或中断：要求动作声明可安全重试，且当前合同与运行时已有该动作的成功测试证据，否则先处理或回滚。
- 主体成功、后检查失败：只重跑后检查。
- 继续之前重新检查已完成上游组件的后置条件。

续跑沿用原始恢复基线，重新核对环境 Revision、Release 合同与源码摘要。手工回滚按选定安装范围逆序编排。不要使用 `--start-at-task` 或跳过 tags 续跑。

场景预览和导出接口不创建 Run：`POST /api/v1/scenario-revisions/{id}/job-plan` 与 `POST .../job-bundle`。导出提交预览返回的 `expectedPlanDigest`；介质需要直用或平移选择时，先提交完整 `deliveryDecisions` 并重新预览。Run 已生成的包通过 `GET /api/v1/runs/{id}/job-bundle` 下载。


新生成的原生作业使用 `clusterforge-native-job-v3`。初始化和最终完成由专用控制 Play 确认；阶段入口使用动态 Role 保持私有变量，并用独立静态入口进行语法预检。Ansible 2.8 会截断 `tasks_from` 子目录，因此平台在封装时生成可审计的导入入口，原始组件文件保持原样。

完整交付必须包含所有组件及场景验收。`GET /api/v1/runs/{id}/job-bundle?verified=true` 汇总同一锁定计划的成功尝试链，返回根 Run 的完整作业及证据绑定，不会把最终一次续跑的局部计划当作完整集群流程。普通 Run 下载保持历史快照语义。详细执行方式见 [原生作业包](standalone-role-job.md)。

执行准备检查执行器、SSH、介质和资源合同，并展示组件 YAML 的执行安排。运行条件与现场残留不在准备阶段执行或标记通过；依赖完成后才执行组件前置检查，实际结果记录于 Run。
