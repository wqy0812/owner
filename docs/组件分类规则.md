# 集群安装组件分类规则

## 1. 适用范围

本规则只用于 Kubernetes/OpenFuyao 集群安装，范围从主机准备开始，到集群核心服务、基础插件和可选平台扩展安装完成为止。

不纳入本分层的内容：

- 已有集群的巡检、信息采集、故障修复、配置变更、升级、回滚、清理和删除作业。
- Elasticsearch、Solr、ZooKeeper、HDFS 等业务中间件或数据服务。
- 仅用于演示平台能力的非安装资产；原 Demo Node Agent、Demo Policy Bundle 已从平台目录及其场景、环境和作业中删除。

## 2. 基本分类规则

### 2.1 环境适配条件不是组件

下列信息只描述组件 Release 可以在什么环境中安装，不创建独立组件，也不作为场景 DAG 的安装节点：

| 适配维度 | 当前实例 |
| --- | --- |
| CPU 架构 | x86/amd64、ARM/arm64 |
| 操作系统 | SUSE、Kylin |
| IP 协议族 | IPv4、IPv6 |
| 硬件类型 | 通用主机、GPU、DPU、BMS |
| 容器隔离方案 | runc、Kata、Kata Confidential Containers |
| 部署形态 | standard、serverless、ingress |

这些信息应保存在 `ComponentRelease.environmentConstraints` 中。例如：

```json
{
  "cpuArch": ["amd64", "arm64"],
  "osDistro": ["SUSE", "Kylin"],
  "ipFamily": ["IPv4", "IPv6"],
  "hardwareProfile": ["general", "gpu", "dpu", "bms"],
  "isolationRuntime": ["runc", "kata", "kata-cc"],
  "deploymentMode": ["standard", "serverless", "ingress"]
}
```

### 2.2 以逻辑能力划分组件

一个对象满足下列条件时，才建议作为独立组件：

- 在目标主机或集群中形成可识别的软件能力。
- 有独立版本、交付物、配置或生命周期。
- 能够独立验证安装结果。

Ansible Playbook、Role 或目录不自动等于组件。一个 Role 同时安装 Docker、Flannel、kubelet 和 CoreDNS 时，它是交付 Bundle，其中的软件仍按独立逻辑组件管理。

### 2.3 层级不代表精确执行顺序

层级用于组件展示、检索、权限分工和默认编排提示。实际安装顺序必须由 Release 依赖和场景 DAG 表达，不得仅根据层级号推导。

## 3. 集群安装分层

### L1 主机基础与安全准备层

职责：将裸机准备为可安装集群软件的节点，并准备集群信任材料。

| 组件 | 说明 | 必选性 |
| --- | --- | --- |
| Host Preflight | CPU、内存、磁盘、内核、网络、时钟和系统参数的安装前检查 | 必选 |
| Host Bootstrap/SYSTEM | SSH 信任、账户、目录、基础工具和节点公共配置 | 必选 |
| Cluster PKI/Certificates | CA、etcd、Kubernetes 控制面、kubelet、kube-proxy 等证书 | 必选 |
| Kubernetes Encryption Configuration | API Server 静态数据加密配置，对应现有 `1175encrypt` 能力 | 按安全基线选择 |

当前平台中的 `BKE Certificates`、`BKE Bootstrap`、`Kubernetes 1.17.5 Certificates` 属于本层的交付阶段，不建议与证书、SSH 等逻辑组件重复建模。

### L2 容器运行时与状态存储层

职责：为 Kubernetes 提供容器执行能力和控制面状态存储。

| 组件 | 说明 | 必选性 |
| --- | --- | --- |
| Docker | 现有旧版 Kubernetes 交付路径使用的容器运行时 | 运行时二选一 |
| containerd | CRI 容器运行时 | 运行时二选一 |
| runc | Docker/containerd 的 OCI 容器执行器 | 随运行时方案选择 |
| Kata Containers | 虚拟化容器运行时 | 隔离场景可选 |
| Kata Confidential Containers | 机密容器运行时 | 机密计算场景可选 |
| etcd | Kubernetes 控制面状态存储 | 必选 |

`Kubernetes 1.17.5 Etcd` 是 etcd 在特定集群版本中的安装阶段，应关联到 etcd Release，而不应再定义一种新的软件类别。

### L3 Kubernetes 编排核心层

职责：提供集群控制面、节点管理和 Service 转发能力。

| 组件 | 说明 | 必选性 |
| --- | --- | --- |
| kube-apiserver | Kubernetes API 入口 | 必选 |
| kube-controller-manager | 控制器循环 | 必选 |
| kube-scheduler | Pod 调度 | 必选 |
| kubelet | 节点容器生命周期管理 | 必选 |
| kube-proxy | Service 网络转发 | 按网络方案选择，当前路径使用 |
| kubectl/cluster admin kubeconfig | 集群管理客户端与管理凭据 | 必选交付物 |

如果 kube-apiserver、controller-manager、scheduler、kubelet 始终共用同一 Kubernetes 版本发布，平台可用一个 `Kubernetes` 逻辑组件管理版本，上述项作为子组件。`Kubernetes 1.17.5 Control Plane` 和 `Kubernetes 1.17.5 Worker` 则作为两个可独立执行的交付阶段。

### L4 集群网络、服务发现与存储层

职责：提供 Pod 网络、DNS、API/Service 接入和持久化存储能力。

| 组件 | 说明 | 必选性 |
| --- | --- | --- |
| Flannel | CNI/Pod 网络实现 | CNI 方案二选一 |
| Calico | CNI/Pod 网络及网络策略实现 | CNI 方案二选一 |
| CoreDNS | 集群 DNS | 必选 |
| HAProxy | API Server 或集群服务的高可用入口 | HA 场景可选 |
| Ingress Controller | HTTP/HTTPS 入站流量入口 | 可选 |
| CSI | 容器存储接口及存储驱动 | 按存储方案选择 |
| FSS Storage Integration | 现有 `1175fss`/FSS 相关集群存储集成 | FSS 场景可选 |

IPv4/IPv6 是 Flannel、Calico、CoreDNS、kube-proxy 等组件的 Release 适配条件，不在本层内创建 `IPv4` 或 `IPv6` 组件。

### L5 可观测与节点管理层

职责：在集群初始安装时提供健康、指标、事件、日志和节点管理能力。

| 组件 | 说明 | 必选性 |
| --- | --- | --- |
| Prometheus | 集群指标采集与存储 | 监控方案可选 |
| Prometheus Federation | 多集群指标聚合 | 多集群可选 |
| node-exporter | 主机指标导出 | 监控方案可选 |
| process-exporter | 进程指标导出 | 可选 |
| etcd-exporter | etcd 指标导出 | 可选 |
| kube-state-metrics | Kubernetes 对象状态指标 | 可选 |
| blackbox-exporter | 黑盒探测 | 可选 |
| Event Monitor | 集群事件监控 | 可选 |
| Node Problem Detector | 节点异常检测 | 可选 |
| AMC | 现有节点/集群管理与监控辅助程序 | 交付方案可选 |
| Housekeeping | 节点例行管理能力 | 交付方案可选 |
| Logs/Syslog | 节点和集群日志配置 | 可选 |

本层只收录随集群初始交付安装的能力；安装后的日常日志修改、监控修复等仍属于运维作业，不是新组件。

### L6 平台与可选集群扩展层

职责：在可用 Kubernetes 集群之上安装 OpenFuyao/BKE 平台能力及可选集群扩展。

| 组件 | 说明 | 必选性 |
| --- | --- | --- |
| BKE Common | OpenFuyao/BKE 公共配置和安装前置 | OpenFuyao 场景必选 |
| BKE Addons | OpenFuyao/BKE 集群插件集 | OpenFuyao 场景必选 |
| BKE Management Cluster | OpenFuyao/BKE 管理集群能力 | OpenFuyao 场景必选 |
| BKE Nodes | OpenFuyao/BKE 工作集群节点能力 | OpenFuyao 工作集群可选 |
| Descheduler | Kubernetes 重调度扩展 | 可选 |
| KEDA | 事件驱动弹性扩展 | 可选 |
| OpenKruise | Kubernetes 工作负载管理扩展 | 可选 |
| GPU Support/Exporter | GPU 节点能力和指标导出 | GPU 场景可选 |

`BKE Common -> BKE Addons -> BKE Management Cluster` 可作为 OpenFuyao 管理集群的交付阶段链，但依赖和顺序仍应由场景 DAG 保存。

## 4. 当前平台组件的层级映射

| 当前对象 | 层级 | 对象形态 | 处理建议 |
| --- | --- | --- | --- |
| BKE Certificates | L1 | delivery_stage | 关联 Cluster PKI 组件 |
| BKE Bootstrap | L1 | delivery_stage | 关联 Host Bootstrap 组件 |
| Kubernetes 1.17.5 Certificates | L1 | delivery_stage | 关联 Cluster PKI 组件 |
| containerd | L2 | software | 保持独立组件 |
| etcd | L2 | software | 保持独立组件 |
| Kubernetes 1.17.5 Etcd | L2 | delivery_stage | 关联 etcd Release |
| Kubernetes | L3 | software_bundle | 管理 Kubernetes 整体版本及子组件 |
| kube-proxy | L3 | software | 当确实独立版本和发布时保持独立 |
| Kubernetes 1.17.5 Control Plane | L3 | delivery_stage | 关联 Kubernetes Release |
| Kubernetes 1.17.5 Worker | L3 | delivery_stage | 关联 Kubernetes Release |
| Calico | L4 | software | 保持独立组件 |
| CoreDNS | L4 | software | 保持独立组件 |
| BKE Common | L6 | delivery_stage | 作为 OpenFuyao 交付阶段 |
| BKE Addons | L6 | software_bundle/delivery_stage | 保留 Bundle，同时记录包含的独立插件 |
| BKE Management Cluster | L6 | delivery_stage | 作为 OpenFuyao 管理集群交付阶段 |

## 5. 平台组件元数据合同

平台对安装组件持久化并要求以下分类信息：

```yaml
component:
  layer: cluster_service
  category: network
  kind: software
  requiredness: profile_required

release:
  environmentConstraints:
    cpuArch: [amd64, arm64]
    osDistro: [SUSE, Kylin]
    ipFamily: [IPv4, IPv6]
  dependencies:
    - kubernetes-release-id
```

字段取值：

| 字段 | 取值 |
| --- | --- |
| `layer` | `host_foundation`、`runtime_state`、`orchestration_core`、`cluster_service`、`observability_management`、`platform_extension` |
| `category` | `preflight`、`bootstrap`、`security`、`runtime`、`state_store`、`control_plane`、`worker`、`network`、`dns`、`ingress`、`storage`、`observability`、`node_management`、`platform`、`autoscaling` |
| `kind` | `software`、`software_bundle`、`delivery_stage` |
| `requiredness` | `core_required`、`profile_required`、`optional` |

## 6. 分类冲突处理

- 同一软件因 x86/ARM、SUSE/Kylin、IPv4/IPv6 产生不同 Playbook 时，保留一个 Component，创建不同 Release/Artifact 适配。
- Docker 和 containerd、Flannel 和 Calico 是同层可替代方案，通过场景 Profile 选一，不表达为前后依赖。
- Role 横跨多层时标记为 `software_bundle` 或 `delivery_stage`，不强行赋予单一逻辑层。Bundle 内的独立软件仍各自分层。
- 证书生成属于 L1；证书使用者仍属于自己的功能层，例如 etcd 属于 L2、kube-apiserver 属于 L3。
- 监控、CSI、Ingress 等是否为“必选”由集群 Profile 决定，不通过改变其所属层级表达。
